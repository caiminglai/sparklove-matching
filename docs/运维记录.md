### 2.14 支付回调"先查后改"不原子，同一笔可能发两次货（2026-10-02 已修复）

现象：三个入账口（微信回调 `notify-wechat`、支付宝回调 `notify-alipay`、本机 `mock-pay`）都是这个形状——先 `SELECT` 出订单、JS 里判断 `status === 'pending'`、再 `UPDATE` 成 `paid`、最后 `applyOrderEffect(order)` 发放权益（认证费到账 / 联系方式解锁 / 次数包）。

根因：**判断和写入之间没有原子性**。渠道重复推送（支付宝、微信都会重试通知）或两条通知并发进来，两条请求能同时读到 `pending`，于是各自把状态写成 `paid`、各自发一次货。单次流量下看不出来，一旦渠道重试就会多给权益，`deposits` 里也会多出重复流水。

改法：把状态判断写进 `UPDATE` 本身（`db/payments.js` 的 `updatePaymentOrder`）——`WHERE order_id = $4 AND status <> $1`，返回值改成 `result.changes === 1`。同一笔只有一个请求能拿到 `1`，其余拿 `0`；三个调用方改成**只有返回 `true` 才调 `applyOrderEffect`**，返回 `false` 直接回 `success: true`（对渠道来说这单确实已是 paid，不该再重试）。顺带把渠道交易号用 `COALESCE($3, channel_txn_id)` 写进去，不覆盖已有值。

验证：真 pg（本机 `jzxr-postgres-local`）上在 `BEGIN … ROLLBACK` 里跑——先插一条 `pending` 测试单，第一次带守卫的 UPDATE `rowCount=1`，**第二次同一笔 `rowCount=0`**；去掉 `AND status <> $1` 的对照版本第二次仍回 `1`（这就是原来的 bug）。测试单在事务里回滚，跑完 `payment_orders` 行数与改动前相等，**残留 0 行**。

部署要点：改的是后端两个 js，**烤在 `jzxr` 镜像里** → `docker compose up -d --build jzxr`；`restart` 等于没改。前端 `jzxr-web`、`postgres` 不用动。

现象：他把标价改成 0.01 并真付了认证费与查看联系方式，`https://sparklove.cn/admin/main/` 里"缴费/认证记录"一栏空的。服务器现量 `payment_orders` **16 笔、`paid` 0 笔、`pending` 16 笔（16 笔全是 alipay）、带 `channel_txn_id` 的 0 笔**，`deposits` 与 `contact_unlocks` **各 0 行** —— 后台那两个列表正是读这两张表，所以不是页面坏了，是库里确实没有。再看请求日志：48 小时内 `/api/payment/notify-alipay` **12 条，每一条都是 `200 … 4B`**；4 字节就是那句 `fail`，钱支付宝已经收了，我们这边一笔都不认。而旧代码在拒绝时**一行日志都不打**，所以站内看不出任何原因。

根因：支付宝的通知体是 `application/x-www-form-urlencoded`，**空格的线格式是 `+`**。`routes/payment.js` 里那段内联解析直接把整串按 `&`/`=` 切开后交给 `decodeURIComponent`，而 `decodeURIComponent('2026-10-02+20:04:04')` 得到的是带字面 `+` 的串，不是 `2026-10-02 20:04:04`。`gmt_payment`、`notify_time` 这类字段**永远带空格**，于是拼出来的待签串与支付宝当初签名那一份对不上 ⇒ RSA 验签**必然**失败 ⇒ 每一笔真通知都被当成伪通知拒掉。微信侧是 JSON、没有这个坑，所以只有支付宝全线挂。

改法：① 解码写成独立函数 `decodeFormBody`，先 `replace(/\+/g,' ')` 再 percent-decode，键值都处理；遇到非法百分号转义整个通知按不可信处理（回 `fail` 让支付宝重推），不半解析。② 验签失败/字段不符时打 `[payment] 支付宝通知被拒: <原因> order=… trade_status=… amount=…`，六个拒绝分支各有文案，下次一眼可读。③ 加**查单兜底** `queryAlipayOrder`（`alipay.trade.query`，自建签名 + 切出 `alipay_trade_query_response` 原文验签，照站3 已上线那份的口径），挂在 `GET /api/payment/status` 上：只在"订单仍 pending 且 channel=alipay"时打，按订单 10 秒节流（前端每 3 秒轮询一次），且必须"金额与订单逐笔相符 + 状态属 `TRADE_SUCCESS`/`TRADE_FINISHED` + `updatePaymentOrder` 真的把该行从 pending 翻过来"三个条件同时成立才 `applyOrderEffect`。这一条不是便利功能，是**救回他已付的那几笔**——支付宝会按退避重推，但重推多少次都会栽在同一个解码上，除非改成先纠解码；纠了之后旧单是否还重推不由我们决定，而查单是我们这一侧唯一能主动确认到账的口子。发货不会重复：2.14 那条 `WHERE … AND status <> $1` 的原子守卫正是这里的保险。

验证：离线工装从**已发布的源文件里按大括号配对抽出真实函数**（`decodeFormBody`、`verifyAlipaySign`、`extractResponseNode`）再断言，**18 项全过**（`TOTAL_FAILS=0`、退出码 0）。机理用同一份支付宝通知原文做正反对照：旧解析得到 `gmt_payment="2026-10-02+20:04:04"` ⇒ `verify=false`；新解析得到 `"2026-10-02 20:04:04"` ⇒ `verify=true`；把原文里的 `+` 全换成 `%20` 再喂新解析仍 `verify=true`（对不用 `+` 的发送方无回归），字段级逐条与标准 `URLSearchParams` 解码比对 **漂移 0**。负向三条同轮补测：另生成一把密钥冒充本站应用私钥去自签通知，喂支付宝那把公钥 **验不过**，而喂它自己的公钥 **验得过** —— 说明拒绝来自密钥不匹配、不是签名构造写错，校验确实只认支付宝的公钥；签完之后再改 `total_amount`（0.01 → 29.90）同样验不过，即金额被改动一个字节就过不了闸。非法百分号转义（`a=%zz`）不抛异常、整个返回 `null`，处理器据此回 `fail` 而不是半解析。

未验到 / 待办：① 线上那 12 笔要等他 pull + `docker compose up -d --build jzxr` 之后，由支付宝重推或前端轮询触发才会落账——**改代码不动镜像等于没改**。② 落账后必须复查 `deposits` / `contact_unlocks` 真的长出行，且后台那一栏不再空白。③ 服务器侧的 `ALIPAY_PUBLIC_KEY` 是否真的是"支付宝公钥"而非"应用公钥"，本机用证书对做过自签自比，但线上这把没配错这件事只能由一条真实通知的成功落账来证明。
