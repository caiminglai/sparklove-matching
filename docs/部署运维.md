容器方式（现行，**不要再依赖 `backend/.env` 副本**）：
容器内的环境变量由 `E:\website\compose\docker-compose.yml` 的 `jzxr.environment` 提供，注入的变量名为：
`NODE_ENV`、`PORT`、`API_PREFIX`、`FRONTEND_URL`、`SERVER_ORIGIN`、`ADMIN_USERNAME`、`ADMIN_PASSWORD`、`ENCRYPTION_KEY`、`TOKEN_SECRET`、`PG_HOST`、`PG_PORT`、`PG_DATABASE`、`PG_PASSWORD`、`EMBEDDING_PROVIDER`、`EMBEDDING_API_URL`、`EMBEDDING_API_KEY`、`EMBEDDING_MODEL`。
密钥类取值一律来自 `E:\website\compose\.env` 的 `${VAR}` 引用（该文件不进 Git）；`backend/.env` 只是被只读挂载进容器，dotenv 不会覆盖 compose 已注入的值。

> **支付类密钥是例外**：`DEPOSIT_AMOUNT`、`CONTACT_UNLOCK_AMOUNT`、`WECHAT_*`、`ALIPAY_*` 共 13 项**不在 compose 的 `jzxr.environment` 注入清单里**，只能写在 `2.my-two-website/backend/.env`（该文件被只读挂进容器，且被站2 `.gitignore:10` 排除，不进 Git），由 `server.js` 的 dotenv 读取。名字与说明见 `backend/.env.example` 的支付段。
> 其中两个标价键只是**兜底默认值**：日常改价在后台「价格设置」页做（写进 `admin_settings`，dotenv 只在进程启动时读 `.env`，改这个文件必须重启容器才认），不用动 `.env`。该页 4 个档位——诚意认证费 29.9、查看联系方式 9.9／次、3 次包 25.9、5 次包 39.9，四项都是一次性服务费、支付后不退，各自独立，没有「几档之和等于另一档」的保存约束。两个次数包的价能改，包容量（3／5 次）写在代码里，改了要重建。
>
> **两把支付宝密钥必须写成单行**：dotenv 一行只认一个值，多行 PEM 会被截断。所以 `ALIPAY_PRIVATE_KEY` / `ALIPAY_PUBLIC_KEY` 要把换行转义成字面 `\n` 写成一整行（`-----BEGIN PRIVATE KEY-----\nMIIE...\n-----END PRIVATE KEY-----`），`payment.js` 的 `loadKey()` 负责还原成 crypto 认得的 PEM；也可以直接贴无 PEM 头的 base64，同样一行。

**`NODE_ENV` 的正确用法（易搞反，看代码顺序）：** `backend/server.js:3` 是先按 `process.env.NODE_ENV` 决定加载 `.env` 还是 `.env.production`，**之后**才 `dotenv.config()`。所以：
- 写在 `.env` 文件里的 `NODE_ENV=production` **不会**让第 3 行改读 `.env.production`（求值时文件还没被解析），它只是解析后才进 `process.env`；
- 真正会改变行为的是**进程环境**里的 `NODE_ENV=production`（shell export、compose 的 `environment`）：那时会去找并不存在的 `backend/.env.production`，dotenv 静默失败，整份 `.env` 被忽略；
- `db/index.js:7` 的 `_isProd` 同样只看进程/已解析后的 `process.env.NODE_ENV`，一旦为真，缺 `PG_PASSWORD` / `TOKEN_SECRET` / `ENCRYPTION_KEY` 就直接 `throw`（`:108-117`）。
- compose 目前注入的是 `NODE_ENV=development`（`docker-compose.yml:74`）——这是有意为之，改成 production 前必须先确认 `.env.production` 的加载路径问题已处理。
- 也正因为线上进程环境是 `development`，「假支付」不能用 `NODE_ENV` 来拦：只要有一个渠道的密钥没配齐，`/api/payment/create` 就会落到 mock 分支，任何登录用户 GET 一次 `/api/payment/mock-pay` 就能把订单标成已付（认证费入账、次数包到账同样会被白送）。现在这条分支要 `ALLOW_MOCK_PAY=1` 才打开（`payment.js` 的 `mockPayAllowed()`），线上保持不写这个键，本机调试时才临时开。

必填项：`PG_PASSWORD`、`ADMIN_PASSWORD`、`TOKEN_SECRET`、`ENCRYPTION_KEY`。后两项非 prod 时会退回代码里写死的 dev 兜底值，**生产不能依赖兜底**，且更换密钥会导致旧 token 全部失效、旧加密联系方式无法解密。
`PG_HOST` 在容器内必须是 compose 服务名 `postgres`，写 `localhost` 连不上（`docker-compose.yml:75`）；线上裸机则仍是 `localhost`。

**向量嵌入配置说明：**
- `EMBEDDING_PROVIDER`：向量服务提供商，`openai` 或 `mock`（开发测试用）
- `EMBEDDING_API_KEY`：API 密钥，mock 模式下不需要
- `EMBEDDING_MODEL`：向量模型名称，默认 text-embedding-ada-002（1536维）

改完 env 后必须重建容器才生效：`docker compose up -d --force-recreate jzxr`（compose 会重新解析 `environment` 与 `${VAR}`，见 §11）。只 `restart` 不会重读 compose 文件。

## 7. 部署流程（每次改代码后）

本地改完 → 提交推送 → 服务器只从 Git 拉 → 重建镜像。前端 `dist` 由 `Dockerfile.frontend` 在镜像内构建，**不再手工上传**。

```bash
# 本机：改完代码先构建再验证（在 E:\website\compose 下执行）
docker compose up -d --build jzxr jzxr-web

# 服务器：只从 Git 拉，不手改代码
cd /var/www/2.my-two-website && git pull
cd /var/www/compose && docker compose up -d --build jzxr jzxr-web

# 验证
docker compose ps
docker compose logs --tail=50 jzxr
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:4000/
curl -s -o /dev/null -w '%{http_code}\n' 'http://127.0.0.1:4000/api/users?page=1&pageSize=1'
```

三条铁律：

1. 改了代码必须带 `--build`，否则跑的还是旧镜像里的旧代码。
2. 服务器上**不手改代码**，一切先落到 Git 再 `git pull`。
3. 自增序列：种子 dump `match_db_pg15.sql` 末尾**已接上序列重置块**（2026-09-21 追加，原 dump 自带 11 行 `setval(seq,1,false)` 会让管理端写入撞 `23505`），所以**重灌即自带修正，不用再手工补跑**。`data/reset_sequences.sql` 保留且**在 Git 里**（`.gitignore` 是 `data/*` + `!data/reset_sequences.sql` 精确放行，`git pull` 就能拿到），需要单独重跑时用它（幂等 DO 块，实测 11 列）。只有种子 dump 不入库，需单独传，里面是 602 条**测试**用户数据（脚本生成，非真实用户）。追加动作的验收判据：`stat -c %s match_db_pg15.sql` 从 `663371` 变成 `664110`，增量正好等于 `reset_sequences.sql` 的 739 字节，本机与服务器两边都应停在 664110。

## 9. 故障排查速查

### 9.1 快速诊断流程

**容器方案（本机与服务器同一套）：**

```
现象：网站打不开（502）
  |
检查容器是否在跑：docker compose ps
  |
查看后端日志：docker compose logs --tail=100 jzxr
  |
查看前端容器日志：docker compose logs --tail=100 jzxr-web
  |
查看数据库日志：docker compose logs --tail=100 postgres
  |
HTTPS / 反代异常（仅服务器）：docker compose logs --tail=100 caddy
```

### 9.2 常见问题速查表

| 现象 | 原因 | 解决方法 |
|:---|:---|:---|
| 网站打不开（502） | 后端或前端容器没起来 | `docker compose ps` → `docker compose up -d jzxr jzxr-web`，再看 `docker compose logs jzxr` |
| API 返回 404 | 请求前缀不在前端容器代理范围内 | 前端容器只转发 `/api/`、`/uploads/`、`/avatars/`、`/admin/`（`frontend-server.mjs:39`）；后端是 `server.js` 手写 pathname 分发，未匹配统一 404 |
| API 返回 500 | 数据库表不存在或缺字段 | 代码里没有 `initTables()`；启动时由 `db/index.js:30 initConnection()` 建池探活、`db/vector.js:5 initVectorTables()` 建向量表与 HNSW 索引、`db/payments.js ensurePaymentColumns()` 给 `payment_orders` 补 `channel_txn_id`、`credits` 列（`server.js` 启动期依次调用，均幂等），重启后端即重跑一次（`docker compose restart jzxr`） |
| `.env` 修改不生效 | 变量由 compose `environment` 注入，容器没重建 | `docker compose up -d --force-recreate jzxr` |
| 用旧的 `localhost:4000/jzxr/...` 书签进不去 | 前缀已废除 | 直接访问 `http://localhost:4000/` |
| 前端刷新后 404 | SPA fallback 没命中 | 由 `frontend-server.mjs` 提供 fallback，确认该请求没被当成代理前缀转发出去 |

## 11. Docker Compose 部署（现行方案，本机已整站验证）

> 本节就是现行部署方式。本地与服务器共用同一份 compose，差异只落在同目录 `.env`；站2 在 Docker 中拆为前端、后端、数据库三个服务。
> 本地与服务器共用 `E:\website\compose\docker-compose.yml`（服务器上为 `/var/www/compose/docker-compose.yml`），两端文件保持一致，差异只落在同目录的 `.env`。
> ⚠️ 上服务器前先准备好 `compose/.env`；站2 的种子 SQL 不在 Git 里，必须单独 scp。

| 服务 | 容器 | 构建 | 端口 | 说明 |
|:---|:---|:---|:---|:---|
| `jzxr-web` | `jzxr-web-local` | `Dockerfile.frontend`（多阶段：`npm ci` + `vite build` → 零依赖静态服务） | 宿主 `4000` → 容器 `80` | 前端 SPA，根路径 `/`；`/api`、`/uploads`、`/avatars`、`/admin`（后端自己发的管理后台页面）反代到 `jzxr:8080`；两张收款码 `wechat-qr.png` / `alipay-qr.png` 由 Vite 从 `app/public` 拷进 `dist` **静态托管**（不在代理前缀内） |
| `jzxr` | `jzxr-local` | `Dockerfile`（仅后端） | `127.0.0.1:8080` → 容器 `8080` | 后端 API `/api/*` + 管理后台页面 `/admin*`（公网经 `jzxr-web` 转发进来，宿主端口仍只绑回环） |
| `postgres` | `postgres-local` | `pgvector/pgvector:pg18`（与服务器 PostgreSQL 18 对齐） | 宿主 `5433` → 容器 `5432` | PostgreSQL + pgvector，库 `match_db`，数据卷 `pgdata` **持久化** |

关键点：

- 前端以根路径部署：`Dockerfile.frontend` 内 `ENV VITE_BASE_PATH=/`、`VITE_API_BASE_URL=/api`。`app/.env.production` 的变量名已由旧的 `VITE_BASE_URL` 修正为 `VITE_BASE_PATH`（与 `vite.config.ts:8` 读取的名字一致），非 Docker 的 `npm run build` 也不再踩坑。**注意 `app/.env.*` 被 `.gitignore` 排除（第 11 行），只在本地存在**；容器构建不依赖它，密钥外的构建参数由 `Dockerfile.frontend` 的 `ENV` 提供。
- **密钥外移**：`ADMIN_PASSWORD`、`ENCRYPTION_KEY`、`TOKEN_SECRET`、`PG_PASSWORD` 等不再写在 compose 里，改由 `E:\website\compose\.env` 提供、compose 用 `${VAR}` 引用；`.env` 已在根 `.gitignore` 排除，不进 Git。服务器部署时在服务器放同名 `.env`、填生产密钥即可。
- **运行策略**：全部服务加 `restart: unless-stopped`；postgres 配 `healthcheck`（`pg_isready`），jzxr 用 `depends_on: condition: service_healthy` 等库就绪；统一 `logging` 上限 `max-size:10m / max-file:3`。
- **pg18 挂载点变更**：PostgreSQL 18 官方镜像数据目录约定变了，数据卷必须挂 `/var/lib/postgresql`（不是旧的 `/var/lib/postgresql/data`），否则初始化报 "unused mount/volume" 失败。
- 数据库初始化：首次启动将 `./2.my-two-website/data/match_db_pg15.sql`（文件名沿用旧名，内容实为 pg18 dump）挂载到 `/docker-entrypoint-initdb.d/` 自动导入，users 基线 602 行。该 SQL 只在数据卷首次为空时执行。
- 前端运行时为 `frontend-server.mjs`（零依赖静态服务 + 反向代理），同源访问免 CORS。
- **HTTPS 方案**：由 `caddy` 容器自动申请/续期 Let's Encrypt 证书，跨平台不绑定任何云厂商，配置文件为 `E:\website\compose\caddy\Caddyfile`（只读挂载到 `/etc/caddy/Caddyfile`）。`caddy` 已是 `docker-compose.yml` 中的正式服务（`docker-compose.yml:178`），用 **compose profile 开关**控制，**不再需要手工取消注释文件**：服务器在根目录 `.env` 写一行 `COMPOSE_PROFILES=https`，此后每条 `docker compose` 命令自动带上 caddy；本地不写该行，caddy 不参与 `up` / `ps` / `down`。启用前提是三个域名的 A 记录已解析到公网 IP 且安全组放通 80/443，否则 ACME 申请失败、容器会反复重启（日志里能看到报错）。

```bash
curl -s -o /dev/null -w '%{http_code}' http://localhost:4000/           # 前端 200
curl -s "http://localhost:4000/api/users?page=1&pageSize=1"            # 经前端代理取真实数据 200
```
