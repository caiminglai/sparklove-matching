## 5. Nginx 配置【线上现行 · 迁移到 Caddy 后作废】

> 服务器目前**仍在运行 Nginx**，本节配置就是线上生效内容（`/etc/nginx/conf.d/my-website.conf`）。
> 迁移到容器方案后，HTTPS 与域名反代由 `caddy` 容器承担：`sparklove.cn` / `www.sparklove.cn` 整域回源 `jzxr-web:80`，`/api`、`/uploads`、`/avatars` 等路径规则改由容器内部（`frontend-server.mjs` / Express）处理，本节与仓库 `docs/nginx/` 下的 `.conf` 一并转为存档。**迁移尚未执行**，目标方案见 §13。

配置文件：`/etc/nginx/conf.d/my-website.conf`

### 5.1 your_other_domain.com 完整配置（v6.2 线上现行，迁移后转存档）

```nginx
# ====== 域名：your_other_domain.com（精准匹配，主域名部署）======
server {
    listen 443 ssl;
    server_name your_other_domain.com www.your_other_domain.com;

    # SSL 证书（Let's Encrypt，自动续期）
    ssl_certificate /etc/letsencrypt/live/your_other_domain.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/your_other_domain.com/privkey.pem;
    ssl_protocols TLSv1.2 TLSv1.3;
    ssl_ciphers HIGH:!aNULL:!MD5;

    # 精准匹配 - 前端静态文件（根路径）
    location / {
        root /var/www/my-two-website/dist;
        index index.html;
        try_files $uri $uri/ /index.html;
    }

    # 精准匹配 - API 代理
    location /api/ {
        proxy_pass http://127.0.0.1:8080;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    }

    # 精准匹配 - 管理后台
    location /admin {
        proxy_pass http://127.0.0.1:8080;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
    }
}
```

### 5.2 HTTP 自动跳转 HTTPS

```nginx
# ====== HTTP 自动跳转 HTTPS ======
server {
    listen 80;
    server_name kxbz365.cn www.kxbz365.cn your_other_domain.com www.your_other_domain.com;
    return 301 https://$host$request_uri;
}
```

### 5.3 子路径部署配置（旧版 /jzxr/ 兼容）

如需保留子路径访问方式（如通过 kxbz365.cn/jzxr/ 访问），在对应 server 块中添加：

```nginx
# 补斜杠（重要！访问 /jzxr 自动跳转 /jzxr/）
location = /jzxr { return 301 /jzxr/; }

# 前端 SPA
location /jzxr/ {
    alias /var/www/my-two-website/dist/;
    index index.html;
    try_files $uri $uri/ @jzxr_fallback;
}
location @jzxr_fallback {
    root /var/www/my-two-website/dist;
    try_files /index.html =404;
}

# API 代理（带子路径 rewrite）
location /jzxr/api/ {
    rewrite ^/jzxr/api/(.*)$ /api/$1 break;
    proxy_pass http://127.0.0.1:8080;
}

# 管理后台（HTML 页面）
location /jzxr/admin {
    rewrite ^/jzxr/admin(.*)$ /admin$1 break;
    proxy_pass http://127.0.0.1:8080;
}
location /jzxr/admin/ {
    rewrite ^/jzxr/admin/(.*)$ /admin/$1 break;
    proxy_pass http://127.0.0.1:8080;
}

# 用户上传文件
location /jzxr/uploads/ { alias /var/www/my-two-website/backend/uploads/; }

# 收款码图片
location /wechat-qr.png { alias /var/www/my-two-website/dist/wechat-qr.png; }
location /alipay-qr.png { alias /var/www/my-two-website/dist/alipay-qr.png; }
```

线上现状（服务器 `backend/.env`，PM2 启动时由 dotenv 读取）
```env
# NODE_ENV 不要写在本文件里（原因见下方「NODE_ENV 的正确用法」）
PORT=8080
FRONTEND_URL=https://your_other_domain.com
SERVER_ORIGIN=https://your_other_domain.com
ADMIN_USERNAME=your_admin_name

EMBEDDING_PROVIDER=openai
EMBEDDING_API_KEY=your_openai_api_key
EMBEDDING_MODEL=text-embedding-ada-002
```

迁移后（容器方式，**不要再依赖 `backend/.env` 副本**）：
容器内的环境变量由 `E:\website\docker-compose.yml` 的 `jzxr.environment` 提供，注入的变量名为：
`NODE_ENV`、`PORT`、`API_PREFIX`、`FRONTEND_URL`、`SERVER_ORIGIN`、`ADMIN_USERNAME`、`ADMIN_PASSWORD`、`ENCRYPTION_KEY`、`TOKEN_SECRET`、`PG_HOST`、`PG_PORT`、`PG_DATABASE`、`PG_PASSWORD`、`EMBEDDING_PROVIDER`、`EMBEDDING_API_URL`、`EMBEDDING_API_KEY`、`EMBEDDING_MODEL`。
密钥类取值一律来自根目录 `E:\website\.env` 的 `${VAR}` 引用（该文件不进 Git）；`backend/.env` 只是被只读挂载进容器，dotenv 不会覆盖 compose 已注入的值。

**`NODE_ENV` 的正确用法（易搞反，看代码顺序）：** `backend/server.js:3` 是先按 `process.env.NODE_ENV` 决定加载 `.env` 还是 `.env.production`，**之后**才 `dotenv.config()`。所以：
- 写在 `.env` 文件里的 `NODE_ENV=production` **不会**让第 3 行改读 `.env.production`（求值时文件还没被解析），它只是解析后才进 `process.env`；
- 真正会改变行为的是**进程环境**里的 `NODE_ENV=production`（PM2 注入、shell export、compose `environment`）：那时会去找并不存在的 `backend/.env.production`，dotenv 静默失败，整份 `.env` 被忽略；
- `db/index.js:7` 的 `_isProd` 同样只看进程/已解析后的 `process.env.NODE_ENV`，一旦为真，缺 `PG_PASSWORD` / `TOKEN_SECRET` / `ENCRYPTION_KEY` 就直接 `throw`（`:108-117`）。
- compose 目前注入的是 `NODE_ENV=development`（`docker-compose.yml:60`）——这是有意为之，改成 production 前必须先确认 `.env.production` 的加载路径问题已处理。

必填项：`PG_PASSWORD`、`ADMIN_PASSWORD`、`TOKEN_SECRET`、`ENCRYPTION_KEY`。后两项非 prod 时会退回代码里写死的 dev 兜底值，**生产不能依赖兜底**，且更换密钥会导致旧 token 全部失效、旧加密联系方式无法解密。
`PG_HOST` 在容器内必须是 compose 服务名 `postgres`，写 `localhost` 连不上（`docker-compose.yml:69`）；线上裸机则仍是 `localhost`。

**向量嵌入配置说明：**
- `EMBEDDING_PROVIDER`：向量服务提供商，`openai` 或 `mock`（开发测试用）
- `EMBEDDING_API_KEY`：API 密钥，mock 模式下不需要
- `EMBEDDING_MODEL`：向量模型名称，默认 text-embedding-ada-002（1536维）

改完 env 后必须重启进程才生效：线上现状 `pm2 restart my-two-website --update-env`（见 §4）；迁移后的容器 `docker compose up -d --force-recreate jzxr`（compose 会重新解析 `environment` 与 `${VAR}`，见 §13）。

## 9. 部署流程（每次改代码后）

> **线上现行流程 = 下方第一步～第五步**（WinSCP 上传 dist + `pm2 restart` + Nginx 不变）。服务器尚未容器化，日常上线请按它执行。
>
> **迁移后要改用的流程（Docker Compose，目前只在本机验证过）**：在编排文件 `docker-compose.yml` 所在目录执行
> ```bash
> git pull
> docker compose build jzxr jzxr-web
> docker compose up -d jzxr jzxr-web
> docker compose logs --tail=50 jzxr
> ```
> 前端 `dist` 由 `Dockerfile.frontend` 在镜像内构建，**不再手工上传**；HTTPS 由 `caddy` 服务承担（需根 `.env` 有 `COMPOSE_PROFILES=https`）。详见 §13。

第一步：本地修改代码，确保所有功能在本地开发环境测试正常。

第二步：构建前端
```bash
cd app
npm run build
```

第三步：上传文件到服务器（使用 WinSCP）
- `app/dist/` 内所有文件 -> `/var/www/my-two-website/dist/`
- 如果改了后端代码：`backend/` 对应文件 -> `/var/www/my-two-website/backend/`

第四步：服务器端操作
```bash
cd /var/www/my-two-website/backend
# 如果有新依赖
rm -rf node_modules && npm install
# 重启后端
pm2 restart my-two-website --update-env
# 如果改了 Nginx 配置
sudo nginx -t
sudo systemctl reload nginx
```

第五步：验证部署
浏览器访问 `https://your_other_domain.com/`，按 Ctrl+F5 强制刷新。

### 10.4 常见错误根因速查

| 现象 | 根因 | 解决 |
|:---|:---|:---|
| 前端 404 | Vite 代理配置错误 | 检查 rewrite 规则 |
| 前端数据空 | API 路径错误 | 检查路径前缀 |
| `/jzxr/admin` 404 | server.js 路由顺序 | `/admin` 路由放静态文件服务前面 |
| `/jzxr/admin/main` 404 | 静态文件服务拦截 | 排除 `/admin/main` |
| 管理页面数据空 | API 路径前缀错误 | 检查 API 路径 |
| 502 Bad Gateway | 后端没启动 | 线上 `pm2 restart my-two-website`；迁移后 `docker compose up -d jzxr jzxr-web` |
| 端口占用 | - | `taskkill /f /im node.exe`（Windows） |

### 11.2 常见问题速查表

| 现象 | 原因 | 解决方法 |
|:---|:---|:---|
| 网站打不开（502） | 后端服务没启动（线上）/ 后端容器没启动（迁移后） | 线上 `pm2 restart my-two-website`；迁移后 `docker compose up -d jzxr jzxr-web` + `docker compose ps` |
| API 返回 404 | 线上：Nginx 代理 location 未覆盖；迁移后：前端容器只代理 `/api/`、`/uploads/`、`/avatars/`（`frontend-server.mjs:39`） | 先确认请求前缀；后端路由是 `server.js` 手写 pathname 分发，未匹配统一 404。线上查 `/etc/nginx/conf.d/my-website.conf` |
| API 返回 500 | 数据库表不存在或缺字段 | 代码里没有 `initTables()`；启动时由 `db/index.js:30 initConnection()` 建池探活、`db/vector.js:5 initVectorTables()` 建向量表与 HNSW 索引（`server.js:496,510` 调用），重启后端即重跑一次（线上 `pm2 restart`、迁移后 `docker compose restart jzxr`） |
| `.env` 修改不生效 | 线上：PM2 不重读 env 文件；迁移后：变量由 compose `environment` 注入 | 线上 `pm2 restart my-two-website --update-env`；迁移后 `docker compose up -d --force-recreate jzxr` |
| `/jzxr` 不加斜杠进不去 | dev server 未补斜杠 | `vite.config.ts` 的 `middleware.before` 会把无斜杠 base 301 到带斜杠；生产以根路径 `/` 部署，不涉及 |
| 前端刷新后 404 | SPA fallback 没命中 | 线上查 Nginx fallback；迁移后由 `frontend-server.mjs` 提供 fallback，确认请求没被当成代理前缀转发 |
| 管理后台登录失败 | 线上：Token 失效或 Nginx `/admin` 配置；迁移后：公网 `/admin` 根本到不了后端 | 线上先核对 Token；**迁移前需先补 Caddy 的 `/admin` 路由，见 §3 的告警**；否则只能走宿主机回环 `127.0.0.1:8080/admin` |
| 图片上传失败 | uploads 目录权限/挂载问题 | 线上 `chmod 755 /var/www/my-two-website/backend/uploads`；迁移后该目录在 `/var/www/2.my-two-website/backend/uploads/` 并由 compose 挂到容器 `/uploads`，未挂载时重建容器会丢上传文件 |
| 管理后台按钮无反应 | main.html JS 语法错误 | F12 控制台定位报错行号 |
| 前端数据空但后端正常 | API 路径前缀错误 | 检查前端请求路径 |
| 上传失败 500 | DEPOSIT_RULES 未定义 | 检查 `routes/upload.js` 顶部导入 |
| 举报列表显示"未知" | 返回字段名不匹配 | 检查 `routes/reports.js` 字段映射 |
| 向量搜索报错 | PostgreSQL/pgvector 未安装 | 确认 PostgreSQL 18 + pgvector v0.8.2 已安装 |
| 向量生成失败 | EMBEDDING_API_KEY 未配置 | 检查 `.env` 中 EMBEDDING_PROVIDER 和 API_KEY |

|------|------|------|

### 11.4 调试铁律

1. 本地启动必须先 cd 进对应文件夹（app/ 或 backend/）
2. 改 env 后必须重启才生效：线上 `pm2 restart my-two-website --update-env`；迁移后 `docker compose up -d --force-recreate jzxr`

## 13. Docker Compose 部署【目标方案：本机已整站验证，服务器迁移待执行】

> 本节是**准备替换 §4/§5/§9 的目标方案**，目前只在本机 `E:\website` 跑通；**服务器尚未迁移**，在那之前线上仍按 §4（PM2）+ §5（Nginx）+ §9 第一~五步执行。
> 迁移完成后本地与服务器共用根目录 `E:\website\docker-compose.yml`（服务器上为 `/var/www/docker-compose.yml`），该文件两端保持一致，差异只落在同目录的 `.env`。站2 在 Docker 中拆为前端、后端、数据库三个服务。
> ⚠️ 迁移前必须先解决 §3 里那条「管理后台公网不可达」的功能缺口，以及根 `.env`、站2 种子 SQL 需单独 scp 等前置条件。

| 服务 | 容器 | 构建 | 端口 | 说明 |
|:---|:---|:---|:---|:---|
| `jzxr-web` | `jzxr-web-local` | `Dockerfile.frontend`（多阶段：`npm ci` + `vite build` → 零依赖静态服务） | 宿主 `4000` → 容器 `80` | 前端 SPA，根路径 `/`；`/api`、`/uploads`、`/avatars` 反代到 `jzxr:8080`；两张收款码 `wechat-qr.png` / `alipay-qr.png` 由 Vite 从 `app/public` 拷进 `dist` **静态托管**（不在代理前缀内） |
| `jzxr` | `jzxr-local` | `Dockerfile`（仅后端） | `127.0.0.1:8080` → 容器 `8080` | 后端 API `/api/*`；`/admin` 只能从宿主机回环或容器网内访问（公网不可达，见 §3） |
| `postgres` | `postgres-local` | `pgvector/pgvector:pg18`（与服务器 PostgreSQL 18 对齐） | 宿主 `5433` → 容器 `5432` | PostgreSQL + pgvector，库 `match_db`，数据卷 `pgdata` **持久化** |

关键点：

- 前端以根路径部署：`Dockerfile.frontend` 内 `ENV VITE_BASE_PATH=/`、`VITE_API_BASE_URL=/api`。`app/.env.production` 的变量名已由旧的 `VITE_BASE_URL` 修正为 `VITE_BASE_PATH`（与 `vite.config.ts:8` 读取的名字一致），非 Docker 的 `npm run build` 也不再踩坑。**注意 `app/.env.*` 被 `.gitignore` 排除（第 11 行），只在本地存在**；容器构建不依赖它，密钥外的构建参数由 `Dockerfile.frontend` 的 `ENV` 提供。
- **密钥外移**：`ADMIN_PASSWORD`、`ENCRYPTION_KEY`、`TOKEN_SECRET`、`PG_PASSWORD` 等不再写在 compose 里，改由根目录 `E:\website\.env` 提供、compose 用 `${VAR}` 引用；`.env` 已在根 `.gitignore` 排除，不进 Git。服务器部署时在服务器放同名 `.env`、填生产密钥即可。
- **运行策略**：全部服务加 `restart: unless-stopped`；postgres 配 `healthcheck`（`pg_isready`），jzxr 用 `depends_on: condition: service_healthy` 等库就绪；统一 `logging` 上限 `max-size:10m / max-file:3`。
- **pg18 挂载点变更**：PostgreSQL 18 官方镜像数据目录约定变了，数据卷必须挂 `/var/lib/postgresql`（不是旧的 `/var/lib/postgresql/data`），否则初始化报 "unused mount/volume" 失败。
- 数据库初始化：首次启动将 `./2.my-two-website/data/match_db_pg15.sql`（文件名沿用旧名，内容实为 pg18 dump）挂载到 `/docker-entrypoint-initdb.d/` 自动导入，users 基线 602 行。该 SQL 只在数据卷首次为空时执行。
- 前端运行时为 `frontend-server.mjs`（零依赖静态服务 + 反向代理），同源访问免 CORS。
- **HTTPS 方案**：由 `caddy` 容器自动申请/续期 Let's Encrypt 证书，跨平台不绑定任何云厂商，配置文件为 `E:\website\caddy\Caddyfile`（只读挂载到 `/etc/caddy/Caddyfile`）。`caddy` 已是 `docker-compose.yml` 中的正式服务（`docker-compose.yml:172-191`），用 **compose profile 开关**控制，**不再需要手工取消注释文件**：服务器在根目录 `.env` 写一行 `COMPOSE_PROFILES=https`，此后每条 `docker compose` 命令自动带上 caddy；本地不写该行，caddy 不参与 `up` / `ps` / `down`。启用前提是三个域名的 A 记录已解析到公网 IP 且安全组放通 80/443，否则 ACME 申请失败、容器会反复重启（日志里能看到报错）。
